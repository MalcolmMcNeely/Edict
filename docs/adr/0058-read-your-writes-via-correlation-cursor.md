# Read-your-writes via correlation cursor

Status: Accepted

A consumer can read a projection row and have the framework wait, briefly and boundedly, until the work a Command set in motion is visible, then answer with a typed tri-state. The Command result carries an opaque `EdictCursor`; the consumer feeds it to a Projection Read as `after:`; the projection grain parks the read until the correlation the cursor names has been applied, then serves the row. This closes the familiar CQRS gap between "the Command said Accepted" and "the projection shows it" without the consumer hand-rolling poll-and-retry, optimistic UI, or a bespoke sequence-number scheme. It rides on the read-through-grain seam (ADR-0057): because the read now routes through the activation that owns the rows, that activation is on the read path and can host the wait.

The token is a **chain-stable correlation id, not an `EventId`**. `EventId` is minted per hop as an event enters the Outbox, so at the far end of a `command → event → [saga] → command → event → projection` chain the projection applies an event whose `EventId` the original caller never saw — a saga in the middle breaks it. Trace context was the only chain stitch before this change, but it is `null` when unsampled, so it cannot back a correctness feature. So Edict mints an explicit `CorrelationId` (a `Guid` field on both `EdictCommand` and `EdictEvent`) and propagates it by one rule: a message inherits the correlation of the message that caused it, and an origin with none mints one. There are three stamp points — `IEdictSender.SendAsync` mints if empty (honouring a caller-supplied value), a Command's raised Events inherit the handling Command's correlation as they are enqueued, and a Saga's dispatched Command inherits the handled Event's correlation. A timer, schedule, or cap fire has no upstream message, so it naturally starts a fresh correlation through `SendAsync`'s mint-if-empty — correct, because a time trigger is a new causal root. The id falls out as a free grouping dimension on dead-letter rows.

The cursor is **`readonly record struct EdictCursor(Guid CorrelationId)`**, `[MessagePackObject(keyAsPropertyName:true)]`, echoed on `EdictCommandResult.Accepted` (`sealed record Accepted(EdictCursor Cursor = default)`). It is a wrapper rather than a bare `Guid` for type safety and so the surface can widen later without a wire break, and its public constructor lets a caller who supplied their own correlation build a cursor without round-tripping `Accepted`. The `= default` keeps every existing `new EdictCommandResult.Accepted()` consumer site compiling: the runtime stamps the real cursor after the handler returns, so a consumer handler never threads the correlation by hand.

The read result is a **typed tri-state, never a throw**. `EdictProjectionRead<TRow>(TRow? Row, EdictReadStatus Status)` for a point-get and `EdictProjectionPartitionRead<TRow>(IReadOnlyList<TRow> Rows, EdictReadStatus Status)` for a partition query, with `Status ∈ { Immediate, CursorReached, CursorTimedOut }`. Eventual-consistency lag is an *expected* outcome and belongs in a result, not an exception — the same reasoning that routes business rejection through `EdictCommandResult` rather than a throw (ADR-0041). A `CursorTimedOut` read still returns the latest available row, flagged, so the consumer decides what to do with possibly-stale data; an evicted (forgotten) correlation degrades to that same plain read rather than erroring. The one legitimate throw is `OperationCanceledException` on caller cancellation.

One token-optional seam expresses all three read modes through `(after, timeout)`, so there is no second method. `after: null` answers immediately from current store state — the poll path, `Immediate`. `after: cursor` with a bounded `timeout` waits, resolving `CursorReached` or `CursorTimedOut`. `after: cursor` with an explicit `Timeout.InfiniteTimeSpan` waits indefinitely, resolving only `CursorReached` (or surfacing cancellation). **Indefinite must be explicit**: an omitted `timeout` on a cursor read falls back to the bounded `EdictOptions.ProjectionReadTimeout`, never to infinite, so a forgotten timeout cannot hang a request. This mirrors the `EdictSchedule.Unbounded` explicit-opt-out idiom, and indefinite is safe because an in-flight grain call pins the activation, keeping the in-memory wait-list alive.

The mechanism is a **correlation ring plus a wait coordinator on the projection grain**. The ring is a bounded, persisted record of recently processed correlation ids, modelled directly on the existing dedup ring (a `Guid[]` with head and count, pure `Apply`/`RollBack` transitions and an in-memory mirror). It lives in a new nullable `GrainEnvelope.CorrelationProgress [Id(5)]` slot, populated only by projection roles and null for every other role — exactly the pattern of the saga lifecycle slot, costing one empty reference for grains that never read-your-write. Extending the shared dedup state was rejected: it is used by every idempotent consumer and would allocate the ring on grains that have no use for it. The persisted ring advances on the existing dedup-ring commit, so tracking processed correlations costs no extra write, and it is persisted so read-your-writes survives a projection deactivate and reactivate. A separate tunable `EdictOptions.CorrelationWindowSize` (default 100) sizes it, distinct from `IdempotencyWindowSize`.

The processed-correlation marker ties to **store-visibility, not ring-commit**, so a `CursorReached` answer implies the row is readable. The persisted ring advances in the main grain-state commit, which lands *before* the `UpsertRow` effect drains, but the live "is this correlation processed" check that the coordinator consults reads an in-memory mirror updated *post-drain*, after the row write has landed (a hook on the outbox commit, gated on the effect leaving `Pending`). A read interleaving between commit and drain therefore does not see the correlation yet, parks as a waiter, and is signalled at end-of-turn once the row is in the store. The persisted ring is consulted only at activation, where drain-on-activation has already made the store consistent, so it re-seeds the mirror against a settled store. On the crash path the marker correctly lags until the recovery drain writes the row. Net: correct store-visibility with zero extra hot-path writes. The grain read methods carry `[AlwaysInterleave]` (ADR-0057) precisely so a parked wait does not hold the activation's only turn while the stream-delivery turn that would satisfy it queues behind, self-deadlocking.

`CursorReached` is **any-applied, documented as such**. When one correlation produces multiple events to the same projection, the marker is recorded on the first applied, because all-applied is unknowable without an event-count wire concept that fights the dynamic fan-out of ADR-0010, and multiple `Raise` calls per Command (hence per correlation) are a supported shape. The honest contract is therefore: *`CursorReached` means at least the correlation's first effect on this projection is visible.* The mitigation is guidance, not enforcement — the docs and the `edict-authoring` skill recommend preferring one Event per Command where exact read-your-writes matters; no analyzer enforces it, since enforcing it would break legitimate batch publish.

`Edict.Testing` gains **no cursor or timeout seam**. Read-your-writes is a flow property the existing store-reading projection probe already proves: send the Commands, drain, read the row. The cursor wait, the timeout against the injected `TimeProvider`, the tri-state resolution, ring eviction, propagation, and any-applied semantics are all pure in-grain logic, unit-tested in `Edict.Core.Tests` against a virtual clock with no wall-clock delay. One persistence-axis conformance scenario binds the end-to-end across Azure Table and Postgres — send a Command, capture the cursor, force a projection reactivation, read with the cursor, assert `CursorReached` with the row reflecting the write — because that path exercises grain-state persistence and a real store round-trip; the timeout, eviction, and any-applied paths are a recorded conformance skip as they have no backend dependency.

This builds on ADR-0057 (projection reads through the grain), ADR-0002 (the dedup ring this ring is modelled on), and the contracts boundary of ADR-0007 (the cursor and the two new correlation fields are MessagePack wire material with stable concrete shapes, no `[Union]`). It supersedes nothing: it adds the read-your-writes capability on top of the read-through-grain foundation.
