# Release via a manual-dispatch button, notes from commit prefixes

Status: Accepted

Releases are cut by a **`workflow_dispatch` button** in GitHub Actions, not by typing and pushing a `v*` tag from a terminal. The dispatch takes a `bump` choice (`patch` / `minor` / `major`) and a `dry_run` checkbox. A single workflow computes the next version as `latest v* tag + chosen bump`, creates and pushes the tag, then builds, tests (full suite excluding throughput/benchmarks), packs, pushes to NuGet, and publishes a GitHub Release. MinVer continues to derive the package version from the tag, unchanged. Release notes are generated by `git-cliff` from Conventional-Commit prefixes on the squash-merged commits since the last tag, grouped into sections; `docs:` and `chore:` commits are filtered out so the notes carry only consumer-relevant change (`feat:`, `fix:`, breaking).

The bump is a **deliberate human choice every release**, never derived from the commits. `major` performs a literal semver jump — from `0.x` it goes to `1.0.0` — with no `0.x`-special remapping; the operator owns that decision. A `dry_run` release runs the full pipeline (tests included) but skips the real tag, the real NuGet push, and the GitHub Release, pushing instead to the NuGet test gallery so the pipeline can be smoke-tested without minting a version. The pre-existing `push: tags: v*` trigger is retained on the same workflow as a manual escape hatch (release from a terminal if Actions is unavailable); a button-created tag does **not** double-fire it, because GitHub suppresses the tag-push trigger for tags pushed with the default `GITHUB_TOKEN` — the same suppression that makes the single-workflow design necessary.

Operating procedure lives in `RELEASING.md` (the *how*); this ADR is the *why*. The one discipline the automation depends on is recorded there: notes are only as good as commit subjects, since `git-cliff` reads the `feat:`/`fix:` line verbatim.

## Considered Options

- **Manual-dispatch button with an explicit bump choice (chosen)** — kills the terminal-typing pain while keeping the major/minor decision a per-release human judgment. Predictable, least machinery, no secret to rotate.
- **Conventional-commits auto-derivation (`semantic-release` / `versionize`)** — rejected: it removes the explicit lever the maintainer wanted for occasional major/minor bumps, demands flawless `BREAKING CHANGE:` annotation discipline to ever cut a major, and most such tools impose `0.x`-special semver remapping (mapping "breaking" to a minor bump) that conflicts with wanting `major` to mean a literal `1.0.0`.
- **Two workflows chained by a Personal Access Token** — rejected: pushing the tag with a PAT so a separate `publish.yml` fires on it adds a scoped secret to create, store, and rotate, a classic source of silent breakage a year out. The single-workflow design needs no PAT because it never relies on the tag trigger.
- **GitHub-native categorized notes via `.github/release.yml`** — rejected as the notes source: GitHub categorizes by PR *label*, not by commit prefix, so it would require per-PR labeling discipline (or an auto-labeler) that the existing `feat:`/`fix:` prefixes already make redundant. `git-cliff` reads the prefixes the maintainer already writes.
- **A committed `CHANGELOG.md`** — rejected: for a library whose consumers read NuGet and the GitHub Releases page, an in-repo second copy is a maintenance surface that drifts. The Releases page is the canonical history.
