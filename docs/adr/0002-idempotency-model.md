# Idempotency model

Edict's stream provider is at-least-once, so events can be redelivered on crash or handler exception. Every event carries a mandatory `EventId` (Guid) assigned at publish; consumer grains (event handlers, sagas, projection builders) inherit `EdictIdempotencyBase`, which maintains a **bounded, per-consumer window of recently-seen `EventId`s in the grain's own persisted state** and suppresses redeliveries — scope is per-consuming-grain, so legitimate fan-out to different consumer types is never suppressed. Delivery is a template method: the base checks the window, runs `HandleAsync`, and **commits the `EventId` only after `HandleAsync` succeeds**, so a thrown handler is genuinely retried. The accepted limitation is that a redelivery arriving after more than _window-size_ subsequent events is not recognised as a duplicate — the window is sized for realistic redelivery latency, and ADR 0001 forbids replay so arbitrary-age redeliveries do not exist.

## Delivery is interleaved, not serial (amended in place)

The check-run-commit template above is correct but its first reading hides a concurrency hazard, because the dispatch interface (`IEdictEventConsumer.OnEdictEventAsync`) is `[AlwaysInterleave]`. That attribute is load-bearing — it prevents a saga or projection builder from deadlocking against itself when a fan-out cascade re-enters the same activation — but it means two redeliveries of the **same `EventId`** can run concurrently on one grain. The naive template straddles the persisting `await` over `HandleAsync`: the window `Contains` check happens before the await and the `EventId` commit happens after it, so a second concurrent delivery of the same id passes the check during that window before the first has committed, and both run `HandleAsync`. The window is consulted at check time but only written at commit time, so it cannot suppress a duplicate that is already in flight.

This is closed with a **transient in-flight reservation** held alongside the durable window in `DedupRingMirror`. Before dispatch, each path replaces the bare `Contains` gate with `TryClaimInFlight(eventId)`, which reserves the id if it is in neither the committed window nor the in-flight set and fails the claim otherwise; a failed claim is suppressed as a dedup hit exactly as a committed-window hit is (same span and counter, distinguished only by a bounded `reason` tag, `window` | `in_flight`). The reservation is in-memory only — it is never persisted, is no part of the idempotency state, and is rebuilt as empty on activation — so it adds no wire or persisted-state change; it exists solely to close the concurrent window between check and commit. The claim is applied **uniformly across all four dedup-guarded delivery paths** (projection-base inline dispatch, saga inline dispatch, event-handler staging, pointer-envelope intake), not only the two that await inline today, so that a future `await` added to a currently-safe path cannot silently reopen the race.

The two invariants the original model relied on are unchanged. **Commit-after-success** still holds: the durable window commit stays inside the post-`HandleAsync` atomic grain-state write, so a thrown handler still leaves the window unwritten and is genuinely retried. **Write-fault-then-redeliver** still holds: the in-flight reservation is released in a `finally`, on both success and fault, while the committed window only gains the id on a successful write — so a handler that succeeds but whose state write faults releases the reservation without committing the id, and the redelivery re-dispatches. The in-flight set narrows the concurrent-duplicate window; it never becomes the durable truth, which remains the committed window.
