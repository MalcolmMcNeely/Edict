# Idempotency model

Edict's stream provider is at-least-once, so events can be redelivered on crash or handler exception. Every event carries a mandatory `EventId` (Guid) assigned at publish; consumer grains (event handlers, sagas, projection builders) inherit `EdictIdempotencyBase`, which maintains a **bounded, per-consumer window of recently-seen `EventId`s in the grain's own persisted state** and suppresses redeliveries — scope is per-consuming-grain, so legitimate fan-out to different consumer types is never suppressed. Delivery is a template method: the base checks the window, runs `HandleAsync`, and **commits the `EventId` only after `HandleAsync` succeeds**, so a thrown handler is genuinely retried. The accepted limitation is that a redelivery arriving after more than _window-size_ subsequent events is not recognised as a duplicate — the window is sized for realistic redelivery latency, and ADR 0001 forbids replay so arbitrary-age redeliveries do not exist.

## Delivery is serial per activation; the in-flight reservation is defense-in-depth (amended in place, then corrected)

A prior amendment claimed delivery is interleaved rather than serial, and that the `[AlwaysInterleave]` attribute on the dispatch interface (`IEdictEventConsumer.OnEdictEventAsync`) was load-bearing against re-entrant deadlock, so two redeliveries of the same `EventId` could run concurrently on one grain. Empirical investigation against real Azure Queue Streams and real Kafka disproved both claims, and the framing is corrected here. A real Orleans pulling agent delivers one stream's events to a single consumer activation **serially** — `RunConsumerCursor` awaits each `OnNextAsync` (the whole turn, including the state commit) before pulling the next batch — and `OnNextAsync` is non-reentrant. So two deliveries to one activation are never in flight together, whether they carry the same `EventId` or different ones; only distinct activations run concurrently. `ProjectionDeliverySerializationScenarios` proves this on both providers (handler-turn high-water mark of one, exact counts).

The `[AlwaysInterleave]` attribute lived only on the Test Framework's delivery seam, never on the production `OnNextAsync`. It was not guarding reentrancy: the harness's fan-out cascade is fire-and-forget (never awaited within a grain turn), so a saga or projection re-entering its own grain cannot deadlock — removing the attribute leaves the saga cascade green. It was silently absorbing the harness's own concurrent fire-and-forget dispatch, and in doing so manufactured a concurrency real Orleans never produces, which corrupted list projections (the over-count flake; see ADR-0062). The attribute is removed, the harness now serializes its own deliveries per activation, and both delivery seams honour one non-reentrant contract — pinned by `EventConsumerReentrancyParityTests`.

The **transient in-flight reservation** (`TryClaimInFlight` over `DedupRingMirror`) remains, reframed as cheap in-memory defense-in-depth rather than a load-bearing fix. Since real delivery is serial, no concurrent same-id delivery reaches one activation, so the reservation closes a window that production single-stream delivery does not open; it is retained only because it is free — in-memory, never persisted, rebuilt empty on activation, no wire or persisted-state change — and guards uniformly across all four dedup-guarded paths (projection-base inline dispatch, saga inline dispatch, event-handler staging, pointer-envelope intake) against any future seam that might await differently. Each path uses `TryClaimInFlight(eventId)` in place of a bare `Contains` gate; a failed claim is suppressed exactly as a committed-window hit (same span and counter, distinguished only by a bounded `reason` tag, `window` | `in_flight`).

The two invariants the original model relied on are unchanged. **Commit-after-success** still holds: the durable window commit stays inside the post-`HandleAsync` atomic grain-state write, so a thrown handler still leaves the window unwritten and is genuinely retried. **Write-fault-then-redeliver** still holds: the in-flight reservation is released in a `finally`, on both success and fault, while the committed window only gains the id on a successful write — so a handler that succeeds but whose state write faults releases the reservation without committing the id, and the redelivery re-dispatches. The in-flight set never becomes the durable truth, which remains the committed window.
