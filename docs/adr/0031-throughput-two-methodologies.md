# Throughput: two methodologies in one document

Status: Accepted

## Context

`docs/benchmarks/throughput.md` is the artefact a stranger cloning Edict reads to answer "what throughput does this framework actually sustain?" One parallelism × scenario sweep cannot serve both readers of that document. The **headline reader** wants a single quotable sustained-EPS number per substrate, measured under a methodology defensible enough to put their name next to. The **engineering reader** wants the tail-latency surface and the Commands / RaiseOnly / Events budget decomposition across `N ∈ {1, 4, 16, 64, 256}`, because those are the numbers that say where time goes when a pipeline is slow. The pre-#144 file had only the second view — a thirty-row table, no top-of-doc number — and the reader had to know the methodology (closed-loop, paced per-issuer by `await`) and pick the peak themselves to extract anything resembling a headline. Closed-loop bounded-concurrency is the right shape for latency distributions and budget decomposition because each issuer's `await SendAsync(...)` correctly serialises producer pressure to the consumer's rate; it is the wrong shape for a sustained-throughput claim because the EPS that falls out is correct-but-implicit — a first-time reader cannot tell whether a 66 EPS row reflects the producer hitting a ceiling or the consumer.

## Decision

The document carries two surfaces — one throughput, one latency — generated from one benchmark invocation. Each answers exactly one question; neither can be misread as the other.

The **saturation pass** is the sole throughput surface. Events only, fixed N=256 producers fire-and-forget for 30 s after a 20 s warmup, a single sum-of-counters read at window-end, no per-event polling, no drain detection. The output is `{{table:saturation}}` — one row per substrate **per projection species**, one `Events / sec (end-to-end)` column — landed at the top of the document as the headline. EPS appears nowhere else in the markdown.

The saturation workload is **counter-per-aggregate**, one row/payload per aggregate, increment-and-write on each event, not row-per-event. The property that earns the choice is fixed-cost end-of-window measurement: 1024 reads summed locally, regardless of how many events were processed. A row-per-event projection would write-amplify with EPS and contaminate either the measurement or the producer, depending on which side blocked first. Per-aggregate grain serialisation means the read-increment-write loop never contends on ETag.

The pass runs once per **projection species** (PRD #349, ADR-0061) over the identical producer workload, so the EPS delta isolates the storage-commit cost: `BenchCounterListProjectionBuilder` ⇒ `benchcounter` table, drained at-least-once via the `UpsertRow` outbox effect and summed store-direct; `BenchCounterStateProjectionBuilder` ⇒ in-grain `BenchCounterProjection` payload, committed inline with the dedup ring and summed through `IEdictProjectionReader<BenchCounterProjection>` (one grain hop per aggregate, at window-end only). Each species runs in its own cluster activating only its own projection so the passes never contaminate each other's consumer write pressure.

The **closed-loop sweep** is the sole latency surface. N issuer tasks each `await sender.SendAsync(...)` (`Command acceptance`) or `await SendAsync + WaitForEventRowAsync` (`Command → Event delivery`), 10 s warmup + 30 s window, latency histograms per issuer, p50/p95/p99 reported. The sweep is narrowed to `N ∈ {2, 16, 64}` — enough range to show how latency scales with concurrency without the pathological-tail rows at very high N that bloated the pre-#155 table. The output is `{{table:closed_loop}}` — twelve rows (two scenarios × three N values × two substrates) with **no EPS column**. Closed-loop's bounded `await` rate-paces the producer, so any per-second figure published from this surface would read as a throughput claim it cannot make; suppressing the column in the markdown is what enforces the framing. The full closed-loop EPS surface (including the wider N sweep and the dropped `RaiseOnly` history before #153) is preserved in the raw CSV alongside per-sample latency, so the audit trail is intact.

The surfaces run on **separate `TestCluster` instances** brought up in sequence per substrate, one per mode: closed-loop (silo registers `BenchProjectionBuilder` only, client registers `IEdictTableWriteStore<BenchEventRow>` only), then the `SaturationList` pass (silo registers `BenchCounterListProjectionBuilder` only, client registers `IEdictTableWriteStore<BenchCounterRow>` only), then the `SaturationState` pass (silo registers `BenchCounterStateProjectionBuilder` only, client registers no store — it reads through `IEdictProjectionReader<BenchCounterProjection>`). Per-mode registration is a delivered code property — `ClusterHarness` keys on `SubstrateStartMode` so the two non-active projections never activate — not a methodology aspiration; pre-#152 Orleans auto-discovery activated every projection grain in every cluster and biased every published number low through multiplied consumer-side write pressure.

Prose lives in `docs/benchmarks/throughput.template.md` and `MarkdownWriter` is a pure-function token replacer over `{{token}}` placeholders. The committed `throughput.md` is entirely regenerated; numbers cannot drift from the data and prose cannot be silently overwritten. The template is the only hand-curated surface.

## Bring-up resilience

The bench brings a substrate's containers up roughly five times per run — once per pass (closed-loop, then `SaturationList`, then `SaturationState`) per substrate — and on a constrained laptop a stalled gvproxy port mapping under stock Testcontainers waits turns a single bad boot into an unbounded hang. This section records the bring-up-hardening decisions so they are not re-litigated or accidentally undone.

**Fresh containers per pass, chosen over ADR-0030's reusable long-lived runtime.** ADR-0030 blesses a per-test-collection `StartAsync` producing a long-lived runtime reused across scenario sweeps, and that is correct for conformance. The throughput bench deliberately does *not* reuse: it stands fresh containers up for each pass and tears them down after. The passes share the `BenchEventRow` workload table, and the saturation Kafka substrate uses a fresh consumer group — a reused substrate carrying a fresh `Earliest` group would replay from offset 0 and a reused table would carry rows across passes, so reuse would contaminate the next pass's counts unless each pass got its own logical-namespace isolation. Fresh-per-pass *is* that isolation, the cheapest version of it. **This is not a contradiction of ADR-0030 to be "fixed" — reintroducing runtime reuse here silently reintroduces cross-pass contamination.**

**Per-pass setup deadline + fail-fast whole-run abort.** Each pass is brought up under a linked-CTS setup deadline (`BringUpTuning.SetupDeadline`, default 5 min, env-overridable) spanning `substrate.StartAsync` + `cluster.DeployAsync` — the token threads genuinely into `StartAsync` and wraps the non-token-aware `DeployAsync` via `WaitAsync` (abandon-on-deadline, with the cluster dispose in the same `try`/`finally` so an abandoned or faulted deploy is reclaimed). A `SubstrateBringUpFailedException` (the harness-local retry-exhaustion failure, deliberately *not* an `Edict*`-typed runtime exception — ADR-0041 governs the consumer runtime, not the harness), a deadline breach, or a Ctrl-C cancellation aborts the whole run with a non-zero exit naming the substrate and phase, **returning before the markdown render** so the published `throughput.md` and every per-substrate sidecar already on disk stay intact.

**Cross-boot settle, within-boot serialize + stagger, lowered env-overridable waits.** `SubstrateBringUpPolicy` owns retry (dispose-and-recreate between attempts, `RetryCount` default 3), within-boot step sequencing with a stagger gap (`WithinBootStaggerGap`, default 2 s), and a per-attempt wait/probe budget. `KafkaPostgresSubstrate` bring-up is two ordered steps — Postgres then Kafka, disposed in reverse on a failed attempt — so two heavy containers do not fight for CPU and disk during initialization. The harness applies a cross-boot settle gap (`CrossBootSettleGap`, default 5 s) between a pass's teardown and the next pass's bring-up so gvproxy can drain. The stock Testcontainers waits are lowered: the in-container readiness wait drops from its silent ~1 h default to `TestcontainersWaitTimeout` (default 90 s), and the host-side readiness probe from 60 s to `HostReadinessProbeDeadline` (default 30 s, polled every `HostReadinessProbePollInterval`, default 250 ms), so a stalled mapping fails fast into a fresh-container retry — the only thing that clears it — rather than eating the setup deadline. Every knob is tunable for a genuinely slow boot via `BringUpTuning.FromEnvironment`; see `throughput.template.md` § Setup for the variable names.

**Harness-only `TimeProvider`, distinct from ADR-0071's production prohibition.** `SubstrateBringUpPolicy` reads all its timing from an injected `TimeProvider` and runs the container lifecycle through a delegate seam, so the resilience logic is proven by clock-free tests with no real Docker. This is the *opposite* of the rule in ADR-0071, and the two must not be conflated in either direction. ADR-0071 forbids injecting the clock into the production reminder cold-start retry, because scheduled grains and fixtures run on a frozen `FakeTimeProvider` where a clock-driven delay would never elapse and the loop would deadlock — so that retry pauses on wall-clock `Task.Delay`. The bench harness is test/tooling code, not the production runtime: injecting `TimeProvider` is exactly right here and is what makes the bring-up policy testable. The wall-clock-only rule applies to the production retry loop; the inject-the-clock rule applies to the harness. Neither is a bug to be "corrected" toward the other.

## Trade-offs

- **No delivery cross-check.** The saturation pass reads a counter at window-end; it does not compare the count to the producer-issued send count `P`. A regression in Edict's at-least-once delivery would surface as lower EPS, indistinguishable from a real bottleneck. At-least-once is owned by the conformance suite, not this benchmark, so the loss of cross-check is acceptable here.
- **No saturation latency surface.** Per-event histograms, percentiles and samples are absent from the saturation pass. The closed-loop table is the only latency surface; if a regression moves tail without moving steady-state EPS, the closed-loop sweep is what surfaces it.
- **Cluster bring-up doubled.** Two `TestCluster` instances per substrate per run pays the silo-startup cost twice. The 20 s saturation warmup overlaps that cost; total runtime impact is under ~15% of the existing closed-loop sweep.
- **Saturation fixed at N=256.** The saturation pass does not sweep parallelism. `Command acceptance` is producer-side-bound at the N=256 the saturation pass uses (the consumer ceiling on `Command → Event delivery` sits well below the per-second rate the producer can issue `SendAsync(...)`s), so N=256 outpaces the consumer on both registered substrates today. A substrate where end-to-end EPS approaches `Command acceptance` EPS would need this revisited.

## Considered Options

- **Replace the closed-loop table with the saturation table.** Rejected as full replacement (the latency surface is not subsumed by a single-substrate-single-number row); landed as a **reduction**. Closed-loop kept as the latency surface but stripped of its EPS column and narrowed to `N ∈ {2, 16, 64}` × two scenarios via #153. Engineering readers still get the latency surface for tail-latency regressions; the throughput claim sits on the saturation pass exclusively.
- **Sweep parallelism for the saturation pass.** Rejected: a sweep would reproduce the closed-loop sweep's shape and dilute the single-headline-number property that justifies the saturation methodology existing. Fixed N=256 is sufficient to outpace the consumer on both substrates today.
- **Apply saturation methodology to `Command acceptance` as well.** Rejected: `Command acceptance` is producer-side-bound in the closed-loop sweep at high N (the handler increments durable state and returns, no `Raise`, no stream hop), so saturation methodology would not produce a meaningfully different number — it would just rate-limit the producer's `SendAsync(...)` loop the same way `await` does. Restricting the headline pass to the consumer-bound `Command → Event delivery` workload keeps it focused on end-to-end consumer ceiling. The `RaiseOnly` scenario this entry originally also named was dropped from the bench entirely via #153; it was a producer-side diagnostic, not a reader-facing throughput question.
- **A drain-detection signal at window-end (wait for `count = P` before reading).** Rejected: drain detection turns an open-loop pass into a closed-loop pass that happens to start with a fire-and-forget burst, and the burst's queued backlog would be drained at the consumer's rate after the window — the reported EPS becomes (sum / time-to-drain), which is the same shape as closed-loop. The grilling session called this out as collapsing the methodology distinction.
- **Row-per-event saturation projection (`BenchProjectionBuilder`).** Rejected: write-amplifies with EPS, so the consumer-side write pressure climbs with the very throughput being measured, biasing the result low. Counter-per-aggregate is the fixed-cost shape end-of-window measurement requires.
- **Idempotent regions / preserved-hand-edit markers in `throughput.md`.** Rejected: the template is the only hand-curated surface, and `throughput.md` is entirely regenerated. Idempotent regions invite drift between the marker and the surrounding generated content; the regenerable-template design is the cleaner version.
- **`AutoOffsetReset = Earliest` for the saturation Kafka substrate.** Rejected: fresh-group consumers under `Earliest` would replay the warmup-window backlog into the measurement window, dragging the row down to the rate the consumer can chew through backlog rather than the rate it can absorb live events. `Latest` is the steady-state-throughput signal the saturation methodology needs; the Kafka substrate honours both `SubstrateStartMode.SaturationList` and `SaturationState` (each mapping to the same fresh-group `Latest`) through `ISubstrate.StartAsync(ct, mode)`.
- **Schema-registry-style versioning of the template.** Rejected: if the token vocabulary changes, the template is hand-edited at the same time. Template-format migration tooling is overkill for one document.

## Out of scope

- **Moving the actual ceiling.** Multi-silo `TestCluster`, real Azure Storage account behind a config flag, `QueuePollingPeriod` / `PartitionCount` tuning sweeps. These are where the headline number genuinely moves. This ADR covers the *methodology framing* and *presentation* of two views; it does not commit to any specific ceiling, and a future slice that introduces a real-cloud headline run will land its own ADR amendment or successor.
- **A "saturation"-style headline for non-throughput numbers.** Cold-start latency, recovery time after a substrate fault, dead-letter promotion latency — these have their own measurement contracts and will not be retro-fitted into the saturation table.
- **CONTEXT.md additions for "saturation" / "sustained EPS".** These stay benchmark-methodology terms, not domain terms. The glossary is for the framework's runtime concepts; the benchmark's vocabulary lives in its own doc.
