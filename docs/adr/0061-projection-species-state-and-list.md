# Projection species: in-grain state and external list

Status: Accepted

Edict splits the projection-builder role into **two sibling species over one abstract root**, so a consumer chooses where a read model lives by which base they derive. A **State Projection Builder** (`EdictProjectionBuilder<TProjection>`) keeps the read model in the grain's own durable state; a **List Projection Builder** (`EdictListProjectionBuilder<TListProjection>`) keeps it in an external keyed store. Both derive from `EdictProjectionBuilderBase<TPayload>`, which owns the read-your-writes cursor mechanism (ADR-0058) and the correlation stashing, so the only thing that differs between species is storage and commit shape. This relates to, and does **not** supersede, ADR-0011 (table-projection consistency) and ADR-0013 (persistence-agnostic table projection): both remain the record for the List species.

The motivating gap: before this change the only read-model primitive always wrote to an external store. That is correct for large or unbounded read models, but for the common case of a **small, hot, per-aggregate** read model (one object per grain) it pays an external round trip on every read, an asynchronous `UpsertRow` outbox drain on every write, and a read-your-writes wait that cannot resolve until that drain lands. The State species removes all three: the read model is the `Payload` slot of the persisted grain envelope, committed **inline** with the dedup ring in the single grain-state write, with no outbox effect. Structurally it is a saga without `Dispatch` — it closes the idempotency base on a consumer state type exactly as `EdictSaga<TProgress>` does, and exposes a `Projection` accessor the handler mutates, mirroring `Progress`. The trade-off the consumer is choosing is explicit: in-grain state is cheaper to commit and read but inflates activation latency, so it is for read models the consumer keeps deliberately small.

The **naming** is deliberate. The bare `EdictProjectionBuilder<TProjection>` is the in-grain species and the root is `…Base`, so the simplest mental model ("a projection keeps its read model in the grain") maps to the simplest name, and `List` reads as the escalation for read models too large to hold in a grain. An earlier change had misnamed the abstract root `EdictProjectionBuilder`; renaming it to `EdictProjectionBuilderBase<TPayload>` frees the bare name for the species a consumer actually derives and makes the base type alone signal the species. The readers are symmetric for the same reason: `IEdictProjectionReader<TProjection>.ReadAsync(key)` for the in-grain species, `IEdictListProjectionReader<TListProjection>` (`GetAsync`/`QueryPartitionAsync`) for the external one. Both route through the projection grain, so the read API carries no storage detail either way. Rejected alternative: keeping the bare reader name bound to the List species and giving the in-grain reader a qualified name — it would leave the bare *builder* name meaning in-grain while the bare *reader* name meant external, a permanent split-brain. This is a breaking public-surface rename, taken pre-v1 (no released consumers) to keep the taxonomy honest rather than carry a misnamed root forever.

Making read-your-writes work for the State species required **one shared-path change** to the outbox commit boundary. The cursor coordinator is signalled by an `onDrained` callback that previously fired only after a staged effect drained. The State species stages no effect — the payload write *is* the commit — so without a change the coordinator would never be told the correlation was processed and every cursor read would block to `CursorTimedOut`. The fix fires `onDrained` immediately after a successful state write when there is no staged effect (the payload is already durable at that point). This is safe for every other caller: sagas' lifecycle and schedule commits and the command-handler raise path pass no `onDrained`, plain event handlers pass a no-op, and the List species always stages an effect, so only the in-grain commit path takes the new branch. The consequence worth recording: read-your-writes is actually *tighter* for the State species than for List, because there is no asynchronous drain between commit and visibility.

The split touches every surface that classifies a projection by its base type, and those failures are **silent** (code compiles, the generator emits nothing, no diagnostic), so the repoint is load-bearing: the source generator's type classifier, the `EDICT009` projection-handler analyzer, the read-route registrar, and the MCP handler scanner all move to match the renamed root (for "is this a projection at all") or the concrete generic (for "extract the state type"), and the MCP `HandlerRole` gains a `StateProjectionBuilder` member alongside `ListProjectionBuilder`. A generator test that asserts **both** species are discovered and emitted is the guard against a future edit quietly dropping one. Telemetry and a new `Edict.Testing` seam are recorded skips: the State species reuses the existing handle span and stages no effect, so it adds no new observability surface. Conformance was originally a recorded skip too — the reasoning being that the State species' persistence is plain grain-storage `WriteStateAsync` (already exercised by the saga and command-handler scenarios), its stream delivery rides the same idempotency-base path, and it fires on stream events rather than a clock. That skip was **reversed by PRD #410** (see ADR-0068): the determinism-hardening sweep held that re-applying-and-accumulating durably across a real reactivation is the State species' distinguishing property and deserves its own backend proof, so the species is now bound on both persistence providers (Azure Table + Postgres) alongside the List species.

The performance claim that motivates the State species is made honest in the throughput bench rather than asserted: the saturation pass runs the identical per-aggregate-counter workload through both species and reports them side by side, so the EPS delta isolates storage-commit cost (inline single write versus `UpsertRow` drain), with the activation-cost caveat stated in prose so the number is not read as "always use grain state."
