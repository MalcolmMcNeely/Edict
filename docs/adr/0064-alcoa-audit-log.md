# ALCOA++ audit log

Status: Accepted

Edict ships a regulator-grade audit log a consumer turns on at wiring time: an immutable, attributable, tamper-evident record of *what the system decided, when, on whose authority, and with what outcome*, committed atomically with the decision and queryable to reconstruct any decision chain. The reference bar is **ALCOA++** (Attributable, Legible, Contemporaneous, Original, Accurate, Complete, Consistent, Enduring, Available). Orleans offers nothing usable off the shelf — the log-consistency providers persist state not a queryable record, `RetrieveConfirmedEvents` is per-grain and version-ranged, and the stream is a non-rewindable transport — so the log is built on the outbox primitive Edict already runs. This ADR records the *capture* design; the principal it attributes to is ADR-0063. GDPR **erasure** machinery (per-subject encryption, crypto-shred, dead-letter/claim-check remediation, the data-subject field) is explicitly **deferred to a follow-on ADR**: this design defers erasure, not capture.

**Capture is at two choke points, not the stream.** C1 (`EdictCommandHandler.ValidateAndHandleAsync`) records the command decision; it is the *only* place that sees a rejection — a `Rejected` `EdictCommandResult` raises no event and is invisible to any stream-based scheme, yet "why was this *denied*, and who tried?" is a regulator's first question. E1 (the outbox enqueue point where `EventId` is minted once and `CorrelationId` inherited) records each event. An audit List-projection subscribed to the event stream was rejected as the capture mechanism precisely because it captures events only, never commands and never a rejection; it remains valid as a *secondary* read model over the store. Capture is **synchronous-durable**: the record stages into the same grain-state write that commits the action, so it exists before the action is acknowledged (the only way to honour *Complete* + *Contemporaneous*), while the write to the backing store happens on an asynchronous drain so the grain turn never pays remote-write latency. One record per fact, no double-counting: a command that raises two events yields one C1 record plus two E1 records; a rejected command yields exactly one. The existing dead-letter promoter (DL1) is unchanged and becomes a forensic *sibling*.

**`EdictAuditRecord` is a standalone type, not a unified forensic record with the dead-letter row.** The theorycraft floated one canonical type with an `Accepted`/`Rejected`/`Failed` discriminator of which dead-letter is the failure specialisation; we rejected it because that discriminator conflates two different lifecycle moments — a decision's accept/reject outcome at capture time versus a delivery failure that fires *later* on outbox-drain exhaustion — and it would drag a shipped surface (`EdictDeadLetterEntry`, its repository, projection, and classifier) into the blast radius. The record carries a `Command`/`Event` kind, `Accepted`/`Rejected` plus `EdictRejectionReason[]` on commands, the principal, the `CorrelationId`, the message type identity, `OccurredAt`, and the chain hashes. Whether the two forensic schemas should later share an extracted core is a recorded follow-on, not a v1 deliverable; the maintainer's judgement was that unifying them now "would quickly become technical debt."

**The record holds references and hashes; the body lives in a separate, separately-addressable store.** Inlining the payload into the immutable hash chain was rejected — it welds permanent personal data to the tamper-evident structure and could never be shredded later without breaking the chain, the exact dead-letter `PayloadJson` mistake. Instead the chain link stays personal-data-free (attribution, spine, outcome, a payload **hash**, and a payload **reference id**), and the body is captured to a dedicated `IEdictAuditPayloadStore` keyed by the record id — distinct from the claim-check store, which is event-only, `EventId`-keyed, and on the delivery lifecycle. This satisfies ALCOA *Original*/content reconstruction now (the body is captured and retrievable via `GetPayloadAsync`) while keeping the door open for the deferred crypto-shred, which can encrypt and destroy that slice without touching a single hash. v1 bodies are plaintext at the application layer, encrypted-at-rest by infrastructure; per-subject erasure is the follow-on.

**Tamper-evidence is a per-aggregate hash chain, never a global one.** A single global chain needs one sequencer grain — the bottleneck grain Orleans explicitly warns against, serialising the whole fleet. Each Command Handler grain chains its own records (`prev_hash` in its state, `this_hash` over the **stored record bytes**), which proves "show me this aggregate's unaltered history" — the question regulators actually ask — and reconstructs global order at query time from `CorrelationId` + `OccurredAt`. Hashing the stored bytes rather than a fresh re-serialization makes verification immune to a MessagePack version bump. Global cross-aggregate tamper-evidence via periodic off-hot-path Merkle anchoring is a real later capability, deferred. The chain is per-command-handler grain; sagas, projections, and event handlers do not capture in v1.

**The store is two dumb persistence seams reached through the substrate boundary** (ADR-0030/0042), provider-implemented so `Edict.Core` learns no storage SDK: `IEdictAuditStore` (the queryable chain) and `IEdictAuditPayloadStore` (the bodies). On **Postgres** (the first substrate) the chain is an append-only table guarded by a `BEFORE UPDATE OR DELETE` trigger that raises `insufficient_privilege`, giving tamper *prevention* as well as *evidence*. A trigger rather than a bare `REVOKE UPDATE/DELETE` because the table owner and a superuser bypass `REVOKE` entirely, so only a trigger actually refuses the mutation regardless of the connecting role; the chain hash is still the cross-role *evidence* layer underneath it. On **Azure** the chain is an Azure **Table** (chosen for queryability, writing fan-out append rows per access path — cheap because the store is append-only and Postgres, not Azure, is the throughput substrate) and the payload an **Immutable Blob**; the honest consequence recorded for consumers is that the Azure-Table chain is tamper-*evidence* (the hash chain) without infra *prevention* until the deferred blob-sealing slice, where Postgres has both. Retention defaults to **infinite** (safest for *Enduring*); the consumer imposes a limit per their industry's regulations, and Edict ships no default deletion. The records drain through a **dedicated `AuditSlice`** parallel to `OutboxSlice`, not the shared outbox, because audit retention (infinite, WORM) is a fundamentally different lifecycle than business-effect delivery (drain-then-drop) and an audit-drain failure is a compliance event, not an effect retry; the slice reuses the executor machinery and the dead-letter backstop. The read surface is `IEdictAuditRepository` (`ByCorrelationAsync`/`ByPrincipalAsync`/`ByEntityAsync`, time-ranged) plus `GetPayloadAsync` and a first-class `VerifyEntityChainAsync`.

**Edict's GDPR posture is recorded here as a load-bearing position, not a disclaimer.** A NuGet library that never touches the consumer's runtime data is **neither controller nor processor** (EDPB Guidelines 07/2020): the consumer who operates the application is the controller, and GDPR legal compliance is theirs. Edict's duty is **Article-25 data-protection-by-design enablement** — give the controller primitives that make compliance possible (minimise-to-reference by default so the chain holds no personal data, the future crypto-shred for the unavoidable personal slice, retention as an operator policy) and never force them into a corner where it is not. The immutability-versus-erasure tension is real and resolves, in priority order, by minimising so the chain has nothing to erase, then crypto-shredding the unavoidable in-chain personal slice (defensible best practice with residual, unsettled legal risk — *not* regulator-confirmed erasure, and surviving ciphertext is most safely treated as still-personal pseudonymised data), then leaning on the Article 17(3) retention carve-outs for the legally-mandated slice. The full erasure *design* is the deferred follow-on ADR; this section is the posture it builds on.
