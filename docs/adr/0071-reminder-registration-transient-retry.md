# Reminder registration retries the silo cold-start window

Status: Accepted

Edict's four durability backstops — the outbox drain, schedule reactivation, the saga absolute-lifetime cap, and the audit drain — each arm an Orleans reminder the first time they need one, and they all funnel through the single `GrainReminderRegistrar`. Orleans' reminder service finishes its asynchronous startup (ring stabilization plus the initial reminder-table load) some time *after* a silo activates, and a reminder operation issued inside that window throws `OrleansException: "Reminder Service is still initializing and it is taking a long time. Please retry again later."` The first arm after a cold start races that window. The race is real in production — a consumer grain that arms a schedule, saga, outbox effect, or audit record in the first seconds of a freshly-started silo can hit it — and it surfaced concretely when the Orleans 10.1→10.2 bump shifted startup timing enough to make a schedule-lifecycle test fail non-deterministically in CI with exactly this exception. This ADR records the resulting retry decision so it is not re-litigated or "fixed" into a frozen-clock hang later.

**Reminder registration retries the cold-start window because Orleans' own guidance is to.** The thrown message ends "Please retry again later," and the condition is transient by construction: the service is mid-startup, not broken. So `ExecuteWithColdStartRetryAsync` absorbs it with a bounded, flat-attempt retry rather than letting the first arm after bring-up fail a backstop. The retry is keyed *narrowly* on the still-initializing signal — a narrow ordinal message match, because Orleans exposes no typed exception for this condition (verified against `Orleans.Reminders` 10.2). The match fails safe: any other `OrleansException` message (or a future Orleans reword) is not caught, so an unrelated reminder fault propagates loud on the first attempt with no delay rather than being silently swallowed by a retry meant for a different condition. The retry is invisible to every caller — the `IReminderRegistrar` interface is unchanged — and silent on the common path, where the service is already started and the first attempt returns with zero added latency.

**It throws on exhaustion rather than swallowing.** When the budget is spent the registrar raises a typed `EdictReminderRegistrationException` (inner exception = the last `OrleansException`). Swallowing would leave an idle scheduled grain whose reactivation reminder never armed — a silent stall, the exact invisible-failure mode the exception philosophy forbids. Exhaustion only occurs when the reminder service was unavailable for the *whole* budget, which is no longer a startup race but a hard, silo-wide reminder outage that Orleans itself flags as needing a silo restart. Failing loud with a stable `Edict*` type is therefore correct: on the saga and outbox event paths the typed throw flows into existing dead-letter handling; on the command paths it propagates to the caller. The exhaustion budget is operator-tunable through `ReminderRegistrationRetryCount` on `EdictOptions` (default 3, rejected below 1 at boot), but the inter-attempt delay is not a knob — the per-attempt block on Orleans' own service-start wait dominates wall-clock time, so the pause is near-cosmetic and stays an internal constant, and the policy is a flat attempt count, not exponential backoff.

**The retry delay is wall-clock time, never the injected `TimeProvider`.** The retry bridges Orleans' reminder-service cold-start, which is wall-clock reality, not domain time. Scheduled grains and test fixtures run on a frozen `FakeTimeProvider`, where a clock-driven delay would never elapse and the loop would hang forever — turning a transient-recovery mechanism into a deterministic deadlock. So the inter-attempt pause is a plain `Task.Delay`, and a standing WHY comment at the delay site marks it so a later well-meaning "make this respect the injected clock" change does not reintroduce the hang. This is the wall-clock side of the four-class clock taxonomy (ADR-0068): conformance *outcomes* are clock-free and seam-driven, but infra cold-start is genuine wall-clock latency and must be waited on real time.

**The exception carries an Orleans serialization codec.** On the command paths the registration runs inside the called grain, so `EdictReminderRegistrationException` is serialized back across the grain→caller hop. It is `[GenerateSerializer] public sealed` in `Edict.Core` so the failure reaches the caller as itself, with its message intact, rather than as an opaque `CodecNotFoundException` that hides why the call failed — the same trap fixed for `EdictCrossTenantAccessException` ([ADR-0067](0067-tenant-isolation-enforcement.md)). Living in `Edict.Core`, it is already covered by the ADR-0070 type-filter allow-list ([ADR-0070](0070-edict-type-filter-for-orleans-allow-list.md)), so no filter edit is needed.

## Consequences

The retry is metric-only, not log-narrated: a counter on the shared meter, tagged `operation` (`register` / `unregister`) and `outcome` (`recovered` / `exhausted`), recorded once on recovery (succeeded after at least one retry) and once on exhaustion (about to throw) — never per attempt, and with compile-closed tag allowlists that clear the cardinality policy (ADR-0039). The condition is therefore observable — an operator can see the race being absorbed and alert on a spike of `exhausted` as a reminder-service health signal — without the registrar narrating the command/event flow. The retry lives inline in the one chokepoint rather than in a generic `OrleansTransientRetry` abstraction: there is one known transient Orleans fault and one type all four backstops funnel through, so a generic helper would be speculative. There is no `CONTEXT.md` term — the retry is not a domain concept a consumer reasons about; the existing Reminder, Schedule, and durability-backstop vocabulary covers it.
