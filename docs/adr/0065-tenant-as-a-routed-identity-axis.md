# Tenant as a routed identity axis

Status: Accepted

Edict adds a **tenant**: the isolation key whose data a Command or Event belongs to, the company wall rather than the acting user. It is the third identity axis on the message, sibling to the **principal** (ADR-0063) and distinct from a future **data subject**: a B2B2C employee authenticates as themselves (principal) but the data belongs to their employer (tenant), so the two are orthogonal and routinely differ. The deployment context is shared persistence and streaming to cut cost while one customer must never see another's, in an app that mixes public and tenant-scoped aggregates. This ADR settles tenant as a *routed* identity axis: how it is carried, how it is keyed, and the one-way door that follows. The isolation-enforcement and honour-side storage decisions (call-filter, RLS, claim-check/dead-letter folding, conformance) are owed to a sibling ADR.

The tenant is an **opaque, consumer-supplied `string`** minted via `EdictTenantId.Of(...)`, a durable field on `EdictCommand` and `EdictEvent` beside `Principal`. String, not `Guid`, for the same reason the principal is a string and one stronger: a tenant id can be any identity-provider slug, and unlike the principal it is *folded into the routed grain and stream key*, so a `Guid`-beside-`string` mix would buy nothing and cost a second codegen path. Because it goes into the key, its character set is a **security boundary, not a convenience**: `Of(...)` admits only a strict safe-everywhere whitelist (`[A-Za-z0-9._-]`) and rejects anything carrying the key delimiter, the claim-check path separator, storage-reserved characters, whitespace, control characters, or non-ASCII. A value that smuggled the delimiter `|` could forge another tenant's key space, so the rejection is at construction, property-tested, and build-gating. This is the one validation Edict imposes where the principal imposes none.

The **carry reuses the shipped principal machine** rather than reinventing it. An edge resolver `Func<EdictTenantId?>` registered by `AddEdictTenant(resolver)` yields the tenant at the originating send; registering it is the multi-tenancy opt-in, and a single-tenant app that registers nothing pays nothing. The same grain-entry relay site that seeds the principal seeds the tenant, and the two are seeded through **one seam, `OriginIdentity.Seed(principal, tenant)`**: seeding one identity without the other is unrepresentable by construction, because a forgotten tenant seed would silently route a later same-turn send into the wrong wall, a cross-tenant leak. The tenant is a *durable field*, not ambient state, because the outbox `SendCommand` effect and schedule fires dispatch commands after a crash or reactivation, across boundaries `RequestContext` cannot survive; the relay is the per-turn slot only, re-seeded from the durable field at every grain entry. Schedule fires inherit the **arming tenant** via `ScheduleEntry` arm-context, the same slot that already persists the arming principal and trace context. The principal-to-tenant mapping is the **consumer's**, never read off the request body: trusting a tenant carried in the message payload is the confused-deputy hole this design exists to close.

Failure is **closed at the origin**: a tenant-scoped origin send that resolves no tenant throws `EdictMissingTenantException` synchronously, before anything is persisted, because routing a tenant-scoped command into the default key space is the leak the feature prevents. Framework-relayed sends (saga `Dispatch`, outbox `SendCommand`, schedule fire) inherit the tenant from the relay or arm-context and are exempt, carrying the `IsCrossTurnLink()` marker exactly as relayed principal sends do. The explicit `SendAsync(command, EdictTenantId)` overload is both the escape hatch for a context-free origin and the **public-to-tenant establishing crossing**: a public aggregate that mints a tenant id from a trusted source (`SendAsync(command, EdictTenantId.Of(companyId))`) is the one sanctioned place the wall is established. The relay never changes the tenant implicitly; a tenant-to-public or tenant-A-to-tenant-B crossing is a privileged operator concern for the sibling ADR, fail-closed by default.

## Keying: uniform string keys and the one-way door

A tenant-scoped aggregate is keyed by **value and behaviour, not by a distinct key type**. All three framework dispatch interfaces (`IEdictCommandHandler`, `IEdictEventConsumer`, the schedule-fireable) bind to `IGrainWithStringKey` **always**, for every consumer, single-tenant included. The consumer never names this key type (no human reads the dispatch interface), so a `Guid`/`string` mix buys nothing and costs a second codegen path. A public aggregate composes its key as `{guid}`; a tenant-scoped aggregate composes `{tenant}|{guid}`. The per-aggregate marker is `[EdictTenantScoped]` on the **route-key type**, not per message: an aggregate is a cluster of messages sharing a route key, so marking the type is coherence-by-construction where a per-message attribute would drift into a leak. `[EdictRouteKey]` correspondingly widens from `Guid`-only to a typed key.

The route key plays a triple role (command grain key, stream key via `StreamId.Create`, projection/saga grain key via implicit subscription) through three separate generator emitters, so the tenant fold lands behind **one internal `Compose(tenant, routeKey)` chokepoint** rather than three. This was verified against the Orleans default stream-id mapper and the Orleans.Multitenant prefix pattern, and proven end to end on real Azure Queue Storage and real Kafka: a composed `"{tenant}|{guid}"` stream key is recovered exactly by an implicitly-subscribed `IGrainWithStringKey` projection grain, with Kafka provisioning one topic per `[EdictStream]` and the tenant living in the key, not the namespace. Edict already stringifies keys for storage, so the move to string keys carries no placement penalty.

The cost is a **one-way door**, taken deliberately and openly. The Orleans key type is compile-time-fixed in the grain interface, so it cannot be `Guid`-off and `string`-on per deployment: choosing string keys means **all grains are string-keyed always**, abandoning the earlier "tenancy-off stays byte-identical Guid keys" deferral-safety property. This is correct pre-v1 with no released consumers and expensive later, so it is taken now. The parseability of the composed key is not incidental: it is what makes the isolation call-filter (owed to the sibling ADR) possible, by letting a grain compare the tenant parsed from its own key against the relay's ambient tenant.

The wire change is **additive, not breaking** — a new `Tenant` field on the base records and new `Edict*` types, nothing removed or re-signatured — with the Verify wire-shape snapshots (ADR-0007) regenerated as a reviewed diff. The route-key-type widening and the composed key format *are* breaking and are taken in their own slice with the breaking-change discipline. `Edict.Contracts` stays free of any identity-provider SDK: the resolver is a `Func`, never a contract dependency.
