# Deterministic conformance — scenarios assert, the waiter layer polls

Status: Accepted

This is a corollary of [ADR-0054](0054-conformance-by-axis-not-substrate-pairing.md). That ADR settled *what* the axis batteries cover and *how the faked axis is kept unassertable*; this one settles *how a conformance scenario is allowed to wait*. The batteries run over real brokers and real stores, so the temptation is to treat them as integration tests where a `Task.Delay` is a reasonable way to "let things settle." It is not. A wall-clock sleep is a non-deterministic correctness gate: it is too short under CI load and the scenario flakes, or it is padded long and the suite crawls, and either way it proves a *schedule* rather than an *outcome*. The whole value of the batteries — catching provider-specific drift that unit tests miss — is undermined the moment a green run depends on how fast the machine happened to be.

The doctrine is one sentence: **scenarios assert, the waiter layer polls.** A `*Scenarios.cs` file asserts an external, order-independent outcome — a committed row, an exactly-once count, a marker `ExceptionType` on a dead-letter row, a metric value, set-equality of captured events — never a delivery schedule. It injects faults at count-addressed points rather than by wall-clock, authors its own stream input, drives timers and drains and deactivations through injected seams, and converges within a bounded number of steps. The waiting itself — every poll loop — lives in a sibling `*Waiters` helper. The split is not cosmetic: it is what lets the drift guard below distinguish a banned wall-clock gate inside a scenario from a benign, deterministic poll inside a helper.

## The four-class wall-clock taxonomy

Every wait a scenario might want falls into one of four classes, and each migrates to a specific seam. The taxonomy is exhaustive — there is no fifth class that legitimately needs `Task.Delay` in a scenario.

**Class A — genuine clock-gate.** The scenario must elapse a real engine timer: a saga `[EdictSagaTimeout]` cap, an outbox backoff. The seam is the injected clock. A fixture opts into `UsesVirtualClock`, which registers a `FakeTimeProvider` ahead of the host's `TryAddSingleton(TimeProvider.System)` so the virtual clock wins, and the scenario calls `AdvanceClock(by)` to elapse the timer deterministically — no production change, because the saga cap and the outbox host already resolve `TimeProvider` from the container. The one trap is that freezing the silo's `TimeProvider` also freezes Orleans' stream pulling-agent timer, so stream-delivered events stop arriving on a frozen clock. The fix is a `*Waiters.PumpUntilAsync(AdvanceClock, condition)` helper that nudges the clock forward in small steps to pump delivery while the cap stays gated by an explicit `AdvanceClock`; this was confirmed at runtime against both the real Azure Queue and the real Kafka pulling agents, which gate on the injected `TimeProvider` exactly as the in-memory reference does.

**Class B — grain-deactivation bridge wait.** The scenario deactivates a grain and must wait until Orleans has genuinely torn the activation down — to prove state reloads, an outbox drains on activation, a dedup ring survives. This class is **not** clock-drivable: Orleans teardown is not gated by the injected `TimeProvider`, so `AdvanceClock` does nothing for it. It needs a dedicated **deactivate-and-confirm** seam: `IConfirmsDeactivation` (the grain stamps an activation id when it activates) paired with `DeactivationWaiter.DeactivateAndConfirmAsync`, which triggers deactivation and then polls the activation id until it changes, returning only once the new activation is live. This seam is the one genuinely new design item the doctrine adds; it generalizes an inline pattern that one schedule grain already carried.

**Class C — negative-assertion settle-wait.** The scenario must prove a *non-event*: an unhandled type produced no effect, a rejected command published nothing, an evicted-or-unhandled event left no ring slot. "Sleep, then assert nothing happened" is the classic wall-clock anti-pattern, because a too-short sleep asserts nothing happened *yet*. The seam is the **sentinel-after** pattern: publish a later, deliberately *handled* sentinel event on the same serially-delivered stream or route key, wait for the sentinel to land, then assert the earlier no-effect event left no trace (the count settles at sentinel-only, the captured set excludes the suppressed id). Because the stream delivers serially, the sentinel's arrival is positive proof the earlier event has already been delivered and discarded — the negative is asserted through a positive signal. The wait must gate on the sentinel's *own identity*, never on a handled count: if the regression under test is a stray extra handle, that leak drives the count to its threshold itself, so a count gate returns before the sentinel lands and the assertion passes blind to the leak. This is the one Class-C trap the `Task.Delay` guard cannot catch — it is a semantically-wrong wait, not a wall-clock sleep.

**Class D — benign poll-loop pacing.** The bulk. A correct loop that drives a deterministic probe — `ForceDrainViaReminderAsync` to force the outbox drain — and gates on a count predicate (`FailedAttempts >= 2`, `PendingOutboxCount == 0`), where the small delay only paces the retry. These are correct *in substance*; their only sin is living physically inside a `*Scenarios.cs` file, where the guard rightly flags them. The migration is mechanical: extract the loop into a `*Waiters` helper (the shared `ConformanceWaiters.WaitUntilAsync` is the common target). No behaviour changes; the poll moves to where polling is allowed to live.

Two further seams keep fault injection count-addressed rather than wall-clock, so a recovery path is driven by *how many times* a thing fails, not *how long* the test waits: `OutboxFaultState` and `StorageFaultState` carry count/index/kind-addressed fields (fail the Nth attempt, the Nth effect, a specific `OutboxEffectKind`) alongside the original unbounded boolean, and `ControllableClaimCheckStore` fails a fetch a count-addressed number of times then heals. These let a partial-failure batch and a transient-recovery path be expressed deterministically.

## The guard

The discipline silently regresses without enforcement — the multi-tenancy epic added six fresh inlined poll loops before the guard existed, which is exactly the proof that a guard is needed. So `ConformanceScenarioWallClockBan` in `Edict.Architecture.Tests` source-scans every `*Scenarios.cs` file and reports any line containing `Task.Delay`. It is built as the binding-completeness trio: a pure matcher, a matcher unit test over synthetic input, and a filesystem-wrapped test over the real project. There is **no allowlist** — the `*Waiters` exemption lives inside the matcher itself (it inspects only files whose name ends `Scenarios.cs`), so the benign Class-D poll loops are exempt by construction rather than by an opt-out list that would rot. The guard lands only after all four classes are migrated; landing it first would paint the build red on day one.

## Boundary with chaos (ADR-0066)

This determinism doctrine and the chaos contract of [ADR-0066](0066-chaos-seed-random-per-run-surfaced.md) are complementary, not contradictory, and the boundary is worth stating so the two are never conflated. Chaos — random-per-run duplicate redelivery and bounded reorder — lives in the consumer harness `Edict.Testing`, which runs over an in-process reference stream and exists to exercise a *consumer's* idempotency tolerance. The conformance batteries are the opposite régime: they run over real brokers and real stores precisely to catch *provider* drift, and they are deterministic by construction (ADR-0054's reference-fidelity contract). A random seed has no place in them — a battery scenario asserts an exact outcome and must do so identically on every run. The two régimes share the at-least-once theme but never share machinery: chaos never enters the batteries, and the batteries never randomise.

## Considered Options

- **Allow `Task.Delay` with an allowlist of "known-good" settle-waits (status quo before this ADR)** — rejected: an allowlist rots, every entry is a latent flake, and it gives no structural account of *why* a particular wait is acceptable. The four-class taxonomy plus the no-allowlist guard replaces "this one is fine, trust me" with "every wait migrates to a named seam."
- **Make the conformance batteries deterministic by mocking the brokers and stores** — rejected for the same reason ADR-0054 rejected it: the entire point of the batteries is real-backend realism. Determinism is achieved by controlling *time and fault injection* through seams, not by removing the real backend.
- **A single generalized clock seam covering every wait** — rejected: it does not exist, because Class-B grain teardown is not gated by the injected `TimeProvider`. Pretending one seam covers everything would have left the deactivation bridge waits on the wall clock. The taxonomy exists precisely because the waits are not homogeneous.
- **Fold the doctrine into ADR-0054 rather than a new ADR** — rejected: ADR-0054 is about coverage architecture (which axis, which battery), and the deterministic-waiting doctrine is a distinct, separately-evolving concern with its own seams and its own guard. A corollary ADR keeps each decision legible on its own.
