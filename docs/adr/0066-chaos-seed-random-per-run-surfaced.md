# Chaos seed is random-per-run, surfaced, and opt-out for characterization snapshots

Status: Accepted

> **Supersedes in part [ADR-0025](0025-chaos-default-models-at-least-once-delivery.md).** ADR-0025 fixed the chaos seed at a single constant (`0xED1C7`) and rejected both a `WithoutChaos` builder method and any seed override, reasoning that an invisible fixed seed makes failures "reproducible from the first run." This ADR keeps the chaos contract (always-on duplicate redelivery and bounded per-subscriber reorder, the RNG-derivation and reorder-scope rules, the `EdictEventHandler` carve-out, and the out-of-scope list) but reverses the seed-determinism and no-opt-out clauses for the reasons below. Everything else in ADR-0025 stands.

A single fixed seed explores exactly one interleaving of the duplicate/reorder space, forever. Running the suite ten thousand times in CI buys no additional coverage, and a consumer who passes that one sequence gets false confidence in their reorder tolerance. The seed defaults instead to **one random `int` per process run**, sourced from the `EDICT_CHAOS_SEED` environment variable when set and otherwise generated once at process start; every `EdictTestApp` in the run seeds from that one value, so per-test determinism holds (each app builds independent `Random` instances from the same seed) and the run as a whole is reproducible. The seed is **surfaced on every run** — written to `Console.Out` once and exposed as `EdictChaos.CurrentSeed` — and a failing run's log therefore always carries it. This removes ADR-0025's objection at its root: the original "reproducible from the first run" property held only because the seed was invisible and constant; surfacing the seed makes reproduction a copy of one printed value, so determinism is no longer a reason to forbid variation.

Reproduction is **override-to-reproduce**, not override-to-escape: setting `EDICT_CHAOS_SEED` pins the whole run *to* a failing seed so the bug reappears, the opposite direction from the per-test `WithChaosSeed` that ADR-0025 feared (which would let an author reseed *away* from a failure). There is no per-test seed knob.

`WithoutChaos()` is added as a **narrow per-test opt-out** for timeline *characterization* snapshots — tests whose `Verify` captures the ordered event surface to document the canonical workflow shape, where duplicate/reorder noise is actively unhelpful and where a varying seed would drift the snapshot every run. It zeroes the chaos probabilities for that one app; it does not weaken the contract, because every invariant-asserting test (the population that actually exercises reorder tolerance) keeps chaos on and now rides the varying seed. The framework's own `ReorderChaosHarnessTests` continues to prove the chaos machinery against a pinned seed, so no consumer test needs to snapshot a chaotic timeline.

## Considered Options

- **Globally randomise the seed, including timeline snapshots** — rejected: timeline `Verify` snapshots record reorder as-arrived and are not normalised, so a varying seed drifts them on every run and CI goes permanently red. `WithoutChaos()` on that small population is the targeted fix.
- **Normalise timeline snapshots back to raise order so they are seed-independent** — rejected: ADR-0025's "reorder visible in the snapshot" property is deliberate, and normalising it away is a larger teardown than opting the handful of characterization snapshots out of chaos.
- **Deterministic-by-default with explore opt-in** — rejected: the coverage win should be the default for both local runs and CI, not a job a consumer must remember to run; surfacing the seed keeps the default reproducible anyway.
- **Per-test `WithChaosSeed(int)` to reproduce a failure** — rejected as in ADR-0025: a per-test knob invites reseeding away from failures. The single env var pins the whole run instead.
- **Per-`EdictTestApp` random seed** — rejected: makes "the seed" plural and reproduction ambiguous; one process-wide seed makes "one CI seed per run, surfaced" literally true.
