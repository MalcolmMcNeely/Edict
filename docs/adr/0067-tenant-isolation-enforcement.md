# Tenant isolation enforcement and storage

Status: Accepted

ADR-0065 settled the **tenant** as a routed identity axis: how it is carried and how it folds into a key. This ADR settles how the fold is *enforced*, *read back*, and *stored* — the runtime side of the **Company Wall** and the honour-side storage that backs it. The storage half (Row-Level Security on Postgres, the claim-check fold, dead-letter tenant-tagging) was deferred until those surfaces had landed; they now have, and the sections below fold them in.

The fold is the primary control and it is **static per aggregate, not dynamic per message**. `EdictKeyComposer.Compose(tenant, routeKey)` returns the bare `{guid}` for a **public** aggregate and `{tenant}|{guid}` for a **tenant-scoped** one, and the generator decides which by reading `[EdictTenantScoped]` on the route-key type once, emitting `Compose(command.Tenant, …)` only for a tenant-scoped aggregate and `Compose(null, …)` otherwise. This matters because the carry relays the tenant onto *every* same-process hop, public commands included (a saga dispatch, an outbox `SendCommand`): a dynamic fold keyed on the runtime `Tenant` field would mis-key a public aggregate the instant a tenant rode it, routing it into a per-tenant key space it was never meant to occupy. Marking the decision in source, where the aggregate's tenancy is declared, makes that drift unrepresentable.

A composed key is **parseable**, and that is not incidental. `EdictKeyComposer.Parse` is the inverse of `Compose`: it recovers the exact tenant and route Guid from a key, or throws `EdictMalformedRoutedKeyException` rather than mis-attribute a row to the wrong tenant. The tenant charset excludes the `|` delimiter and the route Guid is fixed-shape hex, so a composed key carries exactly one delimiter and the parse is unambiguous; a property test over generated inputs gates the build on the round-trip. Parseability buys two things: forensics can answer "which tenant owns this row" from the key alone, and the runtime filter below can compare a grain's own key against the ambient tenant.

The **isolation call filter** is the runtime backstop, registered only when tenancy is on. It is an incoming grain-call filter scoped to command grains — the path a stolen route key would travel — that parses the tenant from the grain's own key and compares it to the calling turn's ambient tenant, throwing `EdictCrossTenantAccessException` on a mismatch. On the common path it is silent: the key was composed from the ambient tenant, so key-tenant equals relay-tenant by construction, and the filter is a comparison that always passes. It fires only on a real divergence — a keying bug that bypassed the chokepoint, or an illegitimate reach into another wall. It does **not** guard projection grains: those ride streams rather than direct calls, `RequestContext` does not survive the stream hop, and their isolation is already structural in the composed stream key. For the comparison to hold on an origin send, the sender seeds the per-turn relay with the send's tenant (and principal, together through the one `OriginIdentity.Seed` seam) before dispatch, so the ambient tenant the filter reads is the one the key was composed from rather than an empty slot propagated from a public web turn.

The relay never changes tenancy implicitly, so the two **sanctioned crossings** — the public-to-tenant establishing send and the privileged operator path — pass by marking the call authorized through a single `RequestContext` flag (`TenantCrossing.Authorize()`), set by the explicit `SendAsync(command, tenant)` overload and honoured by the filter, which records the crossing as a span event rather than denying it. The establishing overload leaves the relay as the caller's ambient tenant so the crossing stays visible to the filter, where the bare overload seeds it; a denial and an authorized crossing both emit a span event, but the happy path stays silent because tenancy is not a per-operation event a consumer watches, and a tenant id is unbounded and must never become a meter tag.

Establishing a crossing is therefore **origin-only**: there is no saga-side establishing overload, and a relayed send (a saga `Dispatch`, an outbox `SendCommand`, a schedule fire) inherits the tenant of the message it reacts to rather than minting one. That inheritance leaves a gap the origin throw cannot cover. The origin stamper fails closed only at a genuine origin; a relayed send is deliberately exempt from it (the per-turn relay carries the inherited tenant, and a relay that legitimately carries none — a public chain, a raw timer fire — must pass untouched rather than fail closed). So a public-origin chain that crosses into a tenant-scoped aggregate carries a **null** tenant past the exempt stamper, and `Compose(null, …)` would hand it the bare `{guid}` key, silently co-mingling tenant-scoped state in the shared default partition — the isolation filter never sees it, because a bare key names no tenant to mismatch against. The **composition-site backstop** closes this: both send paths (the resolver path and the generator fast path) re-check the static tenant-scoped fact of the route after identity stamping and *before* composing a key, throwing `EdictMissingTenantException` when a tenant-scoped route is reached with a null tenant. On the relayed path the throw propagates through the outbox executor to the engine's per-group catch and **dead-letters** as a runtime fault (`ExceptionType = EdictMissingTenantException`), the operator-visible signal that a chain tried to cross a wall mid-relay; at an origin the stamper has already thrown, so the check is defense-in-depth there. The tenant-scoped fact reaches the resolver path as an additive flag on the route descriptor the generator emits (the same static `[EdictTenantScoped]` read that decides the `Compose` argument), and the fast path already carries it as a parameter. This settles the design fork in favour of explicit, origin-only crossings: a relay cannot establish a wall it was not handed.

Reads scope by the ambient tenant exactly as writes compose it. `IEdictTenantScopedListProjectionReader` takes **no partition key**: the framework composes the caller's ambient tenant (from the same edge resolver a send uses) into the partition, so a consumer queries only its own rows and *cannot express* another tenant's partition. The reader's shape is the guarantee — a raw partition key has nowhere to go — and a read with no ambient tenant fails closed rather than scoping to a default partition. A tenant-as-partition List projection recovers its partition from the tenant side of its own composed grain key, so a tenant's whole workforce lands in one partition that the ambient-scoped read addresses. The headline is proven end to end on real Postgres: one tenant lists its own employees while another tenant's identical query returns empty by construction, not by a permission check. Within-tenant authorization — which row a user may see — stays the consumer's job; Edict's wall is the company, not the user.

## Honour-side storage

Per-aggregate surfaces — grain state, the List projection partition — follow the composed key for free: the key *is* the placement, so the same parse that the call filter relies on segregates the rows physically. The honour side is the surfaces the key does **not** reach on its own, where the fold must be re-applied by hand or a row would land fleet-wide. Three matter, and a stolen-key adversarial battery proves each denies on **both** real backends (Azure and Postgres), not just the happy path: a thief holding tenant A's raw route key is turned away at command send, projection read, claim-check fetch, and dead-letter.

The **claim-check fold is mandatory**, not optional, because claim-check holds the largest and most sensitive payloads — the bodies too big for the inline envelope. The store is keyed by the event's own id (ADR-0053) folded behind the tenant, so a body parked under one wall is unreachable from another even at the identical `EventId`: a get from the wrong wall raises the typed `EdictClaimCheckFetchException` rather than returning the bytes. Folding only the inline pointer while leaving the blob fleet-wide would wall the smallest data and spill the biggest, so the fold scopes the backing object itself.

**Dead-letter stays operator-scoped and gains a tenant tag.** It is forensic-only (ADR-0018), read by operators, not tenants, and v1 adds no per-tenant dead-letter read. But a failure on a tenant-scoped grain carries a tenant, so the promoted row records it — recovered from the source grain's own composed key, the static wall parsed back out, never a separate per-message field that could drift from the key. The tag lets an operator filter failures by wall; it does not make the row tenant-addressable. Dead-letter is written under a single literal partition, so there is no tenant-named partition a stolen key could compose to reach another wall's forensic payload — the absence of a tenant read surface is itself the denial.

On **Postgres**, Row-Level Security is a second wall *beneath* the key composition. A `FOR SELECT` policy on the grain-state and projection tables compares the tenant prefix of the row key against a per-transaction `edict.tenant` setting the read path sets from the ambient relay — `SET LOCAL` via `set_config`, **independent of the queried key**. That independence is the whole point: a key-composition bug that addressed the wrong partition would still be denied by the database, because the policy reads the relay, not the key the buggy code formed. It is defense-in-depth, not the primary control, and it is `FOR SELECT` only — writes are ungated, keeping the hot write path free of policy cost. RLS is bypassed by a superuser or a `BYPASSRLS` role, so the backstop is real only when the production connection runs as a **non-superuser, non-`BYPASSRLS`** role; the framework does not create that role (credentials are an operator concern), and the requirement is documented in the Postgres wiring guide.

**Azure Table has no Row-Level Security equivalent, and that asymmetry is stated openly rather than papered over.** On the Azure substrate the controls are keying, the runtime call filter, and conformance — there is no wall *below* the key. This is an accepted v1 position: per-tenant storage accounts would add a substrate-side wall but at a cost the shared-infrastructure goal exists to avoid, so the design does not hold Azure to that bar. The same adversarial battery runs on Azure precisely because the key and the filter carry the whole weight there, with nothing beneath to catch a regression.
