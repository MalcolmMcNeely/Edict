# Edict-owned base for Command Validator

Command Validator is a first-class consumer-facing role — runtime-equivalent in standing to Command Handler, Event Handler, Saga, and Projection Builder — but until this ADR it was the only one without an Edict-owned base. A consumer authored a validator by deriving from FluentValidation's `AbstractValidator<TCommand>` directly, named the class however they liked, and the framework discovered it through `IValidator<TCommand>` resolved from grain DI. The mechanism worked; the surface didn't match. Every other consumer role has a brand-prefixed `Edict*` base (`EdictCommandHandler<TState>`, `EdictEventHandler<TEvent>`, `EdictSaga<TProgress>`, `EdictProjectionBuilder` / `EdictTableProjectionBuilder<TRow>`) so the consumer-facing brand and the framework's discovery-by-base-type pattern are consistent across the role tree. Validators sat outside that tree.

This ADR pins the new base. **`Edict.Core.Commands.EdictCommandValidator<TCommand>` is a public abstract type, `where TCommand : EdictCommand`, deriving from `FluentValidation.AbstractValidator<TCommand>`.** It adds no members. The brand and the discovery-by-base-type are the whole point. FluentValidation remains the rule-authoring surface — `RuleFor`, `When`, `WithErrorCode`, `WithMessage` all work unchanged because `EdictCommandValidator<TCommand>` *is* an `AbstractValidator<TCommand>`. The auto-discovery path (`AddValidatorsFromAssemblies` registered by `AddEdict(assembly)`) is also unchanged because the base still satisfies `IValidator<TCommand>`.

The runtime mechanism documented in ADR-0008 — server-side validation inside the generator-emitted `DispatchAsync`, before `HandleAsync`, in the same Orleans activation turn, with current grain state injected via `ValidationContext.RootContextData[SemanticConventions.Validation.GrainStateKey]`, failures mapped to `EdictRejectionReason`s on `EdictCommandResult.Rejected` — does not change. ADR-0008 stands as the precondition-gate rationale; this ADR supersedes only its mechanism note that the consumer derives from `AbstractValidator<TCommand>` directly. The conformance battery (`Edict.Tests.Conformance/Commands/CommandValidatorScenarios.cs`) and `Edict.Core.Tests/Configuration/ValidatorAutoDiscoveryTests.cs` prove no behavioural regression — the reparent is transparent to FluentValidation.

The new base satisfies the brand-prefix rule on the consumer-facing side. Per `CONTEXT.md` clause (a), a type is `Edict`-prefixed iff a consumer types it — derives from it, applies it as an attribute, or receives/returns it. Consumers derive from `EdictCommandValidator<TCommand>` in the same shape as `{Name}{Role}` — `OrderPlaceCommandValidator`, `PaymentAuthorizeCommandValidator` — matching the handler/saga/projection naming pattern. Clause (b) is widened from "consumer-facing grain bases" to "consumer-facing bases (grain or DI-service)" so the brand-rule wording and the new base are consistent; the widening was committed during the grilling session that produced PRD #243 and is not re-litigated here.

## Considered Options

- **Status quo: raw `AbstractValidator<TCommand>`.** Rejected. The consumer surface for every other Edict role is brand-prefixed; the validator was the lone outlier. An agent asking `edict_list_handlers` "do we have a validator for `PlaceOrderCommand`?" cannot answer without a separate scanner branch keyed on a third-party base type — the framework's discovery-by-base-type pattern breaks at the validator. The consumer-perspective lens recorded in ADR-0047 applies: from the consumer's seat, the validator surface looked inconsistent with the rest of the role tree, and the maintainer-convenience argument ("FluentValidation already has a base") was irrelevant to the consumer reading the role catalogue.

- **An Edict-owned abstraction that hides FluentValidation entirely.** A shape like `EdictCommandValidator<TCommand, TState>` with an abstract `ValidateAsync(command, state) -> ValueTask<IReadOnlyList<EdictRejectionReason>>` that surfaces no FluentValidation types. Rejected. The rule DSL (`RuleFor`, `When`, `WithErrorCode`, `WithMessage`) is the load-bearing reason consumers reach for FluentValidation in the first place. Replacing it with a hand-rolled validation surface would lose the DSL consumers already know and expect, and would force Edict into the validation-engine business — a substrate concern, not a CQRS concern. FluentValidation stays as the rule-authoring surface; the Edict base is a thin brand-and-discovery shim over it.

- **`[Obsolete]` shim on `AbstractValidator<TCommand>` usage for one release.** Rejected. Pre-release, no released consumers, no compat constraints — the Sample reparent in this slice is the cutover. A shim would have widened the consumer surface to two valid bases for a release, doubled the documentation footprint, and added IntelliSense noise for no consumer benefit. The reparent is one Sample validator and its test file.

## Consequences

- `Edict.Core.Commands.EdictCommandValidator<TCommand>` ships as a public abstract type with `where TCommand : EdictCommand`, deriving from `AbstractValidator<TCommand>`. No virtual methods, no abstract overrides, no Edict-specific lifecycle.
- `Edict.Architecture.Tests/PublicSurfaceAllowListTests.EdictCoreAllowList` lists the new type. `EdictCore_PublicTypesMatchAllowList` is the drift guard.
- `Sample.Domain` ships `OrderPlaceCommandValidator : EdictCommandValidator<PlaceOrderCommand>`. The old `OrderPlaceValidator` class and file are gone.
- `Edict.Tests.Conformance/Commands/CommandValidatorScenarios.cs` passes unchanged on every substrate — the reparent is transparent to the validator mechanism.
- `Edict.Core.Tests/Configuration/ValidatorAutoDiscoveryTests.cs` passes unchanged — `AddValidatorsFromAssemblies` still resolves the validator because `EdictCommandValidator<TCommand>` is still an `AbstractValidator<TCommand>`.
- Later slices of PRD #243 extend the brand outward to MCP (`HandlerRole.CommandValidator` + scanner branch), to the analyzer surface (`DuplicateCommandValidatorAnalyzer`), and to the consumer-facing prose (skill bodies, `validators.md`, README). This ADR pins only the base type and its rationale; those slices ride on top.
