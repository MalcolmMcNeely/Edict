# Releasing

How to cut an Edict release. For *why* it works this way, and the alternatives that were rejected, see [ADR-0059](docs/adr/0059-release-via-dispatch-button.md).

## Cutting a release

1. Push everything you want in the release to `main`.
2. Open the **Actions** tab, pick the **Publish** workflow, and click **Run workflow**.
3. Choose a `bump` and decide whether to tick `dry_run` (see below), then run it.

The workflow computes the next version from the latest `v*` tag plus your `bump`, creates and pushes the tag, then builds, tests (the full suite minus throughput/benchmarks), packs, pushes to NuGet, and publishes a GitHub Release. MinVer derives the package version from the tag.

### The `bump` choice

The bump is a deliberate choice every release. It is never derived from the commits.

- `patch` increments the patch (`0.4.2` to `0.4.3`).
- `minor` increments the minor and zeroes the patch (`0.4.2` to `0.5.0`).
- `major` increments the major and zeroes the rest (`0.4.2` to `1.0.0`). This is a literal semver jump. There is no `0.x`-special remapping that turns a "breaking" change into a minor bump. If you pick `major`, you get the next major.

### The `dry_run` checkbox

Tick `dry_run` to rehearse the pipeline without minting a version. It runs the full build and test pass, then pushes the packages to the NuGet **test** gallery (`apiint.nugettest.org`). It does **not** create or push the real tag, does **not** push to `nuget.org`, and does **not** publish a GitHub Release. The generated notes still appear in the run's step summary so you can preview them.

### The `main` branch guard

A dispatch must run from `main`. The workflow fails fast on its first step if dispatched from any other ref.

## Escape hatch: release from a terminal

The same workflow keeps a `push: tags: v*` trigger, so if Actions is unavailable you can tag and push from a terminal:

```
git tag v0.5.0
git push origin v0.5.0
```

That fires the same pipeline against the pushed tag. A tag created by the dispatch button does not double-fire this trigger: GitHub suppresses the tag-push trigger for tags pushed with the default `GITHUB_TOKEN`.

## The disciplines the automation depends on

### Note quality is commit-subject quality

Release notes are generated by `git-cliff` from the Conventional-Commit prefixes on the squash-merged commits since the last tag. `feat:` commits become Features, `fix:` commits become Fixes; `docs:`, `chore:`, and every other prefix are dropped, so the notes carry only consumer-relevant change.

`git-cliff` reads the subject line **verbatim** into the notes. The subject *is* the release-note line. Write it that way: `fix: stop the dead-letter promoter throwing on an unknown effect kind (#412)`, not `fix: promoter bug`.

### Breaking changes must be marked

A breaking change reaches the notes' **Breaking Changes** section only when its commit is marked: a `feat!:` / `fix!:` subject **and** a `BREAKING CHANGE:` footer.

The `!` marker is cosmetic for versioning. Because the bump is a manual dropdown choice, the marker does not derive the bump. But it is the only thing that routes a change into the Breaking section, so a missed marker silently files a breaking change under Features.

A change is breaking when it removes, renames, or alters the signature of a public `Edict*` member, that is, when the public-surface allow-list in `Edict.Architecture.Tests` changes by anything other than a pure addition. Adding-only is a normal `feat:`. The grill / to-prd / to-issues / tdd workflow decides this at grill time and carries it on the issue's `Breaking:` line, so honor that line rather than re-deriving it at commit time.
